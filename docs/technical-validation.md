# 기술 검증 기록

검증일: 2026-10-12. 본문의 시각은 별도 표기가 없으면 Asia/Seoul이다. 원본 로그는 UTC로 기록돼 있다.

## 1. 결론과 증거 수준

별도 Python 프로세스에서 기존 Bongo Cat 로비의 채팅을 수신하고, 같은 형식으로 송신하는 경로를 확인했다. 상대방에게도 송신 내용이 보였다는 사용자 확인을 받았다. 이 결과는 메신저 UI 개발을 진행할 근거지만, 배포 가능한 제품의 완성이나 공식 연동 허가를 의미하지 않는다.

| 구분 | 의미 |
| --- | --- |
| 실행 확인 | 실제 설치 환경에서 API 호출, 콜백 또는 데이터 비교를 수행함 |
| 사용자 확인 | 사용자가 실제 게임 또는 상대방 반응을 확인해 대화에서 알려 줌 |
| 소스 분석 | 설치된 관리 어셈블리의 메타데이터와 IL을 읽어 처리 흐름을 확인함 |
| 설계 제안 | 구현할 방법과 조건을 정리했으며 동작 검증은 남아 있음 |
| 미검증·중단 | 시험하지 않았거나 준비만 하고 실행하지 않음 |

## 2. 시험 환경

| 항목 | 확인 내용 |
| --- | --- |
| OS | Windows, PowerShell 환경 |
| 게임 | Steam Bongo Cat, App ID `3419430` |
| 게임 빌드 | 당시 설치 메타데이터 기준 `25723683` |
| 게임 실행 형태 | Unity 관리 어셈블리와 Windows x64 Steam API DLL이 있는 설치 |
| PoC | Python 3.13, `ctypes`, 게임 설치 경로의 `steam_api64.dll` 로드 |
| 계정·장비 | 한 PC, 현재 로그인한 Steam 계정 |
| 외부 상대 | 사용자가 평소 참여하는 기존 로비 이용자. 사용자 관찰로 표시 확인 |
| 기존 변경 | Auto Chest Opener 패치가 이미 적용돼 있었음 |
| 이번 채팅 PoC의 게임 변경 | 게임 파일 수정·프로세스 주입 없음 |

정식 제품은 설치 위치 자동 탐색과 버전 호환 검증이 필요하다. PoC의 하드코딩된 기본 경로와 인터페이스 선택 방식을 그대로 제품 계약으로 삼지 않는다.

**중요한 제한:** 이번 PoC가 게임 파일을 새로 수정하지 않았다는 사실과 순정 게임 환경에서 검증했다는 말은 다르다. 후자는 아직 확인하지 않았다. 이후 순정 설치 환경의 재현 시험을 우선 수행한다.

## 3. 통신 경로

실험에서 확인한 호출 흐름은 다음과 같다.

1. 현재 프로세스의 `SteamAppId`, `SteamGameId`를 대상 게임 ID로 설정한다.
2. 설치된 `steam_api64.dll`을 로드하고 `SteamAPI_InitFlat`으로 초기화한다.
3. 현재 Steam 계정과 실행 중인 게임의 로비 정보를 확인한다.
4. 별도 프로세스에서 Manual Dispatch 콜백을 처리한다.
5. 로비 채팅 이벤트의 식별자를 사용해 본문을 읽는다.
6. UTF-8 JSON의 `Channel`이 `3`인 메시지만 채팅으로 분류한다.

당시 로드된 인터페이스는 `SteamUser_v023`, `SteamFriends_v018`, `SteamUtils_v010`, `SteamMatchmaking_v009`였다. 로비 채팅 콜백 ID는 `507`로 관찰됐다. 이 번호와 버전은 해당 환경의 관찰값이며 모든 배포 버전에서 고정된 것으로 가정하지 않는다.

기존 로비를 관찰할 때 별도 프로세스가 `JoinLobby`를 호출하지 않아도 콜백을 받았다. 한 PC의 같은 계정으로 관찰한 결과이므로 다른 실행 순서·다른 Steam 환경에도 자동 일반화하지 않는다.

Valve 문서는 로비 송신과 콜백 이후 본문 조회 API를 설명하며, 송신 데이터는 최대 4KB로 제한한다. API 호출 결과와 상대방의 열람 여부는 별개의 증거로 관리한다. [ISteamMatchmaking 공식 문서](https://partner.steamgames.com/doc/api/ISteamMatchmaking)

## 4. 실제 수신 시험

원본: `02-live-receive.jsonl`.

- 관찰 시간: 17:01:30부터 약 55초.
- 로비 관련 메시지 콜백: 713건.
- 그중 채팅 채널 `3`: **1건**.
- 다른 채널: `2` 709건, `4` 1건, `5` 2건.
- 채팅 발신자는 현재 계정과 다른 이용자였으며, 콜백의 발신자와 본문 조회 결과의 발신자가 일치했다.
- 5문자 본문을 UTF-8·JSON으로 해석하고 길이와 해시를 기록했다.
- 상대 이용자의 채팅 원문은 로그에 저장하지 않았다.

따라서 확인한 것은 **상대방 채팅 1건의 실제 수신**이다. 전체 713건을 채팅 수신 건수로 보고하지 않는다. 이 한 건만으로 높은 수신량, 장시간 누락률, 닉네임 조회, 전체 상대방 호환성을 검증했다고 볼 수 없다. 사용자가 직접 입력한 문장인지 게임의 기본 발화인지는 이 기록만으로 구분하지 못한다.

## 5. 비공개 로비 자체 왕복 시험

원본: `03-private-loopback.jsonl`.

현재 계정이 소유한 1인 비공개 로비를 만들고 다른 이용자의 입장을 막은 상태에서 수행했다. 매 송신 전 소유자와 인원 조건을 다시 확인했다.

| 시험 | 확인 결과 |
| --- | --- |
| ASCII | 송신 본문과 수신 본문 일치 |
| 한글 | 송신 본문과 수신 본문 일치 |
| 이모지 문자 | 전송 데이터 왕복 일치. 게임 글꼴·화면 표시는 미검증 |
| 따옴표·역슬래시 | JSON 처리 후 본문 일치 |
| 같은 문장 연속 2회 | 두 번 모두 수신. 본문이 같다는 이유로 한 건을 제거하면 안 됨 |

6건 송신·6건 수신, 순서와 횟수가 일치했다. 기록된 왕복 지연은 184.6–235.4ms다. 이는 같은 계정·같은 PoC 프로세스의 소규모 시험 수치이며 제품 성능 목표나 상대방 수신 지연으로 사용하지 않는다.

시험 종료 후 생성한 비공개 로비를 나갔고 기존 게임 로비 정보가 유지되는 것을 확인했다.

별도의 게임 화면 연동 시험은 `04-native-game-session.jsonl`에 준비와 종료만 남아 있다. 그 세션에서는 송신하지 않았으며, 게임 내 표시 성공의 근거로 사용하지 않는다.

## 6. 기존 로비 송신과 상대방 표시

원본: `06-user-requested-text-send.jsonl`, `08-repeat-1.jsonl`부터 `08-repeat-4.jsonl`.

사용자가 기존 로비에서 시험하도록 요청했고 다음 문장을 지정했다.

> 서드파티 프로그램으로 텍스트 송출 테스트 중입니다

17:13:52에 한 번 송신했다. 이후 사용자 요청으로 같은 문장을 약 15초 간격으로 네 번 더 송신했다.

| 회차 | 송신 요청 시각 | API 수락 | 자기 수신 본문 일치 |
| --- | --- | --- | --- |
| 반복 1 | 17:26:35.747 | 확인 | 확인 |
| 반복 2 | 17:26:51.049 | 확인 | 확인 |
| 반복 3 | 17:27:05.782 | 확인 | 확인 |
| 반복 4 | 17:27:20.763 | 확인 | 확인 |

표의 시각은 API 호출 직전 기록한 송신 요청 기준이다. 자동 재시도는 하지 않았다. 송신 전에 대상 로비가 사전 확인한 로비와 일치하는지, 현재 계정이 구성원인지 확인했다.

사용자는 이후 “채팅은 잘 가는 거 확인했다”고 말했고, **상대방에게는 보이지만 본인 게임의 말풍선에는 보이지 않는다**고 구분해 설명했다. 따라서 상대 게임 표시의 증거 수준은 사용자 확인이다. 상대 PC의 화면 캡처나 자동화된 화면 단정문으로 검증한 것은 아니다.

## 7. UTF-8 및 한글 표시 조사

초기에는 상대방이 문자를 이상하게 보았다는 사용자 전달이 있었다. 원인을 인코딩 오류로 단정하지 않고 실제 게임이 만든 데이터와 비교했다.

설치 어셈블리에서 확인한 흐름:

- 송신: JSON 직렬화 → `Encoding.UTF8.GetBytes` → 로비 송신.
- 수신: `Encoding.UTF8.GetString` → JSON 해석 → 채팅 이벤트.

사용자가 게임에서 직접 다음 문장을 보냈다.

```text
인코딩 확인 가나123
```

17:22:30에 해당 계정의 정확히 같은 문장만 캡처했다. 실제 게임 데이터는 다음 JSON의 UTF-8 바이트와 완전히 일치했다.

```json
{"Channel":3,"Message":"인코딩 확인 가나123"}
```

| 항목 | 실제 값 |
| --- | --- |
| 길이 | 52바이트 |
| 외부 프로그램 생성 결과와의 일치 | 전체 바이트 일치 |
| 후행 NUL | 0바이트 |
| ASCII 전용 데이터 | 아님. 한글이 UTF-8 바이트로 들어 있음 |
| `\u` 이스케이프 | 0개 |
| SHA-256 | `97c2802e18cdfb7581ad9ef1a160a892b65c9e24ca1999d2d63382129051d502` |

원본은 `07-native-reference.jsonl`, 공개 가능한 비교 데이터는 [검증 결과 JSON](evidence/2026-10-12-validation.json)에 있다.

이 비교와 후속 정상 송신 확인에 따라 현재 포맷을 UTF-8로 유지했다. 별도의 인코딩 변경으로 문제를 고쳤다고 기록하지 않는다. 처음 보고된 “외계어”의 정확한 모양과 발생 원인은 확정되지 않았다. 이모지 왕복 성공 역시 게임의 이모지 렌더링 지원을 입증하지 않는다.

## 8. 자기 말풍선이 보이지 않은 이유와 최종 결정

소스 분석에서 `Vfx.CatSpeech.SendSpeech`는 네트워크 송신 후 자기 텍스트와 말풍선 상태를 직접 갱신한다. 개념적인 흐름은 다음과 같다.

```text
게임 입력창
  → 네트워크 송신
  → 자기 말풍선의 텍스트 갱신
  → ShowSpeech 호출

별도 Python 프로그램
  → 네트워크 송신
  → 자기 프로그램에서 수신 콜백 확인
```

게임의 `CatSpeech.Start`는 로비 멤버 데이터가 있는 객체에 수신 표시 함수를 연결한다. Python 송신은 게임의 `CatSpeech.SendSpeech`를 호출하지 않으므로, 자기 말풍선의 로컬 표시 단계를 수행하지 않는다. 사용자의 실제 관찰과 코드 흐름이 이 설명에 부합한다.

자기 수신을 말풍선에 연결하는 표시 전용 실험 모듈을 작성·컴파일했고, 게임 어셈블리 사본의 단일 함수에 두 명령만 추가한 뒤 3,401개 메서드의 기존 본문이 보존되는지 검사했다. 그러나 **게임에 설치하지 않았고 런타임 표시도 시험하지 않았다.**

사용자는 별도 메신저 UI에만 내 메시지가 보이면 충분하다고 결정했다. 이에 따라 게임 수정이 필요한 말풍선 연동을 범위에서 제외했고 적용·재시작 계획도 취소했다. 게임 DLL 수정은 이 프로젝트의 송수신 전제 조건이 아니다.

## 9. 미검증 항목

- Auto Chest Opener 등 기존 변경이 없는 순정 설치에서 재현.
- 두 계정·두 PC를 사용한 반복적인 양방향 실제 화면 검증.
- 수 시간 이상 실행, 절전 복귀, 네트워크 단절, Steam 재시작.
- 게임·앱의 실행 순서, 게임이 종료된 상태, 앱 다중 실행.
- 로비 변경과 송신이 동시에 일어나는 상황.
- 이름·고양이·숨김의 제품 UI 반영, 차단·뮤트·필터 설정. 10월 13일 조회 실험은 아래 추가 기록을 참고한다.
- 메시지 길이 경계, 제어 문자, 잘못된 JSON, 알 수 없는 채널·콜백 크기.
- 게임 업데이트와 Steam API 인터페이스 변경 시 동작.
- 지속 저장·검색·삭제·앱 재실행 후 복구.
- 배포 권한, SDK·설치 DLL 이용 조건, 공개 소스 라이선스.

## 10. 재검증 절차

원본 PoC는 제품 코드가 아니라 로컬 연구 보관본이다. 다음 사람이 같은 결과를 얻으려면 새 환경의 설치 위치, 게임 빌드, 구조체 ABI, 현재 계정·로비부터 확인해야 한다.

1. 기본 모드는 읽기 전용으로 실행한다. 앱 ID·로그인·현재 로비와 초기화 결과를 기록한다.
2. 테스트에 참여하는 상대방이 보낸 알려진 문장을 수신하고 본문을 비교한다.
3. 격리한 로비에서 전송 형식과 같은 문장 반복을 검증한다.
4. 실사용 로비 송신은 해당 시험에 대한 사용자 요청이 있을 때만 수행한다. 횟수와 문장을 제한하고 자동 재시도하지 않는다.
5. API 결과, 자기 수신, 상대방 화면 확인을 서로 다른 결과로 기록한다.
6. 앱을 종료한 뒤 게임·로비 상태가 유지되는지 확인한다.

원본 스크립트 이름은 `steam_probe.py`, `send_once.py`, `capture_native_reference.py`다. 원본에 포함된 폐기된 말풍선 모듈은 재현 절차에 사용하지 않는다.

## 12. 2026-10-13 추가 정적 검토

사용자가 로비 변경 자동 추적과 게임의 특정 사용자 숨김 반영을 질문해 기존 PoC와 설치 어셈블리를 읽기 전용으로 검토했다. 빌드는 `25723683`이며 기존 Auto Chest Opener 패치가 있는 환경이라는 제한은 그대로다. 실사용 로비 이동·숨김 설정 변경·추가 송신은 수행하지 않았다.

- 기존 `observe`는 콜백을 읽는 실험 루프이며 로비를 자동으로 전환하는 제품 상태 관리는 없다. `send_once`의 대상 확인은 송신 전에 바뀐 로비를 감지하는 방어이며 자동 추적 검증이 아니다.
- 사용자별 숨김 값은 `PlayerDataCache`의 정적 사전에 있고, `LobbyMemberInstance.IsHidden` 설정은 해당 캐릭터를 비활성화한다. `CatSpeech.ShowSpeech`는 오브젝트가 비활성이면 표시하지 않는다.
- 확인한 숨김 경로에서 외부 공유·저장 호출은 발견하지 못했다. 현재 PoC에는 이 캐시나 숨김 설정을 읽는 기능이 없다. 자동 반영은 미구현이며 가능한 연동 경로부터 확인해야 한다.
- 전체 채팅 끄기와 언어 필터도 게임의 수신 표시 단계에서 검사한다. 게임 설정을 원시 채팅 데이터가 자동으로 상속한다고 가정할 수 없다.
- Steam 공식 문서는 `m_iChatID`를 콜백 범위에만 유효한 값으로 정의한다. 이를 보관해 영구 메시지 식별자로 쓰던 설계 제안을 제거하고, 콜백 내 본문 복사와 앱 자체 ID로 수정했다. [공식 콜백 문서](https://partner.steamgames.com/doc/api/ISteamMatchmaking#LobbyChatMsg_t)

추가 결과는 [정적 분석 요약](evidence/2026-10-13-static-review.json), 기대 동작과 미결 정책은 [엣지 케이스 문서](edge-cases.md)에 기록했다. 위 결과는 정적 코드 분석과 API 계약 확인이며 실제 로비 전환·숨김 연동 성공의 근거가 아니다.

## 13. 2026-10-13 이름·외형·숨김 조회 실행 검증

후속 요청으로 별도 프로세스에서 로비 13명의 이름·모자·스킨을 읽었다. 장착된 25종의 아이템 정의, 대응하는 64개 게임 스프라이트와 정지 이미지 생성 경로를 확인했고 다른 이용자의 외형 변경도 감지했다.

숨김은 공개 Steam 조회 경로를 찾지 못했으나, 게임 프로세스에 읽기 권한만 요청해 실제 `PlayerDataCache`를 읽었다. 최초 12개 항목이 로비의 다른 이용자 12명과 일치했다. 이어 사용자가 요청한 600초 관찰에서 같은 이용자의 `false → true → false`를 숨김·해제 조작과 대조했고 내 스킨의 변경된 상태와 원상 복원도 감지했다. 12:34:45 KST에 관찰을 정상 종료했다. 파일 수정·DLL 주입·게임 메모리 쓰기는 없었다. 제품 표시·검색·알림 적용 검증은 별개로 남아 있다.

또한 현재 계정의 게임 조회가 다른 App ID를 반환하는 사례를 확인했다. 로비 콜백의 방 번호와 내 계정의 구성원 여부를 대조해 읽기를 계속했지만, 자동 로비 전환이나 송신 대상 선택 검증은 아니다.

자세한 근거·실험 경로·미검증 범위는 [프로필·숨김 검증](profile-sync-validation.md), 최초 조회 결과는 [검증 데이터](evidence/2026-10-13-profile-sync-validation.json), 후속 조작 대조는 [600초 관찰 데이터](evidence/2026-10-13-manual-sync-validation.json)에 있다. 앞선 “숨김 조회 경로 미확보”는 이 실험 전 상태다. 순정 설치·다른 PC·게임 업데이트 호환성은 여전히 미검증이다.
