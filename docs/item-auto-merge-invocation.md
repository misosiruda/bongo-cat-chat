# 아이템 자동 합성 — 원본 함수의 외부 호출 가능성 조사

**현재 상태 — 승인 후 실제 호출 완료:** 아래는 모듈 승인 전 조사와 읽기 전용 확인의 시간순 기록이다. 이후 사용자가 내부 모듈 개발·설치를 허용했고, 원본 `SlotDuplicates` / `TryExchange`를 Unity 메인 스레드에서 호출해 합성 화면이 닫힌 상태로 두 그룹 각각 1회 성공을 확인했다. 요청당 1회·전체 2회로 종료하고 처리기를 해제했다. 현재 구현·검증·남은 인수는 [내부 함수 연결 개발판](item-auto-merge.md)을 따른다. 아래의 미구현·범위 미결정·호출 0회는 당시 조사 단계에 해당한다.

조사일: 2026-10-29. 관련 이슈: [#43](https://github.com/misosiruda/bongo-cat-chat/issues/43). [현재 구현 초안](item-auto-merge.md)과 구분한다.

## 승인 전 조사 판단

사용자가 원하는 것은 합성 화면을 직접 열어 두거나 버튼을 클릭하지 않고 게임의 원본 중복 선택·합성 기능을 사용하는 것이다. 화면 클릭 방식은 후속 구현 방향에서 제외한다.

`ItemExchange.SlotDuplicates()`와 `TryExchange()`는 게임 내부 인스턴스 메서드다. 두 메서드 자체에는 화면 표시 여부로 진입을 거부하는 조건이 없고, 합성 관리자도 메뉴 패널과 별도 오브젝트에 있다. 따라서 게임의 합성 화면을 사용자가 계속 열어 둬야 한다는 조건을 요구사항으로 삼을 근거는 없다. 숨긴 상태의 실제 선택·코루틴·결과 반영까지 검증한 것은 아니다.

**현재 확인한 외부 통신 경로에는 이 두 메서드의 호출 기능이 없다.** 채팅 앱의 읽기 전용 메모리 조회나 Steam 채팅 API가 게임의 C# 인스턴스 메서드를 호출하는 경로는 아니다. 원본 함수 재사용을 유지하려면 게임 안에서 요청을 받아 실행하는 연결 모듈을 별도 검토해야 한다. 이는 `AGENTS.md`의 게임 파일 수정·DLL 주입·패치 제외 범위를 바꾸는 결정이며, 이번 조사에서는 구현·설치하지 않았다.

모든 기술적 경로가 불가능하다는 결론은 아니다. 현재 설치본과 조사 범위에서 게임 변경 없이 사용할 수 있는 합성 호출 경로를 확보하지 못했다는 결론이다.

## 조사 대상과 한계

- 로컬 Steam manifest의 build ID는 `25936063`이다. 사용자의 다른 노트북 설치본과 동일하다고 단정하지 않는다.
- `Assembly-CSharp.dll`, `Assembly-CSharp-firstpass.dll`, `Helper.Runtime.dll`, 기존 `BongoAutoChest.dll`의 총 788개 타입·4,343개 메서드 선언을 열거했다. 메서드 본문의 외부 통신·리플렉션·대상 함수 참조를 검색하고 후보 경로의 IL을 읽었다. 모든 플랫폼·SDK·네이티브 구현의 완전한 분석은 아니다.
- Mono.Cecil로 메타데이터만 읽었다. 게임 어셈블리를 실행용으로 로드하거나 메서드를 호출하지 않았다. Mono DLL의 PE export table, `boot.config`, `level0`의 합성 컴포넌트·오브젝트 계층도 정적으로 읽었다.
- 조사 당시 이 PC의 `BongoCat` 프로세스는 0개였다. 게임 실행, 디버거 연결, IPC 접속·송신, 메모리 쓰기, 실제 인벤토리 교환은 수행하지 않았다.
- 추출 IL·조사 스크립트·비교 결과는 Git에서 제외되는 `research/private/merge-invocation-20261029/`에만 두었다. 게임 바이너리·개인 로그·아이템 보유 목록을 저장소에 추가하지 않는다.

이 PC에는 기존 Auto Chest 패치가 설치되어 있다. 설치 기록이 지정한 원본 백업의 해시를 확인한 뒤 현재 DLL과 원본 백업의 메서드 선언·IL 명령 문자열을 비교했다. 차이는 `MainCat.Update()`와 `ShopItem.Callback(Int32, Boolean)` 두 메서드였고 삭제된 메서드는 없었다. 조사한 합성·IPC 메서드 본문은 이 비교에서 동일했다. 로컬 백업과의 비교이며 배포사 원본 서명 검증을 대신하지 않는다.

## 원본 함수와 화면 상태

| 항목 | 정적으로 확인한 동작 | 의미 |
| --- | --- | --- |
| `SlotDuplicates()` | 진행 중 교환·슬롯·중복 여부를 검사하고 `GetDuplicateItems(false)`·`SlotDuplicate()` 사용 | 원본 중복 선택의 재사용 대상. 독립적인 외부 API가 아님 |
| `TryExchange()` | 현재 슬롯과 `_possibleExchanges`로 `ExchangeRoutine` 코루틴 시작 | 재료·횟수·결과 확인 없이 함수 이름만 호출해서는 안 됨 |
| `ExchangeRoutine` | 게임 상태를 갱신하며 `Heathen...ItemData.Exchange`와 비동기 결과 사용 | 게임 실행 문맥·콜백 처리가 필요함 |
| `CloseExchange()` | 표시 상태를 내리고 합성 탭을 숨긴 뒤 알림·인벤토리 UI 갱신 | 표시 패널과 합성 관리자 수명을 동일시하면 안 됨 |
| `level0`의 ItemExchange | 컴포넌트 path ID `11873`, `Steam / SteamApi` 오브젝트에 연결. 파일상 두 오브젝트 모두 active | 메뉴가 닫히면 관리자가 반드시 사라진다는 가정은 부적절. 실제 실행 상태의 증명은 아님 |
| 그룹 선택 | `_currentCategoryTabIndex`와 탭 변경 이벤트의 `OpenTab(Int32)`에 연결 | 앱에서 지정한 그룹을 원본 선택 문맥에 반영하는 설계가 필요함 |

`IsVisible`을 참조하는 다른 표시·아이템 상태 메서드도 있다. 두 진입점에 직접 표시 조건이 없다는 사실을 전체 호출 경로의 무조건적인 비표시 실행 보장으로 확대하지 않는다. 메뉴 닫힘·다른 창 포커스·최소화·게임 종료는 별개 상태이며 실제 인수가 필요하다.

## 외부 연결 후보

| 후보 | 확인한 내용 | 판단 |
| --- | --- | --- |
| 게임의 named pipe IPC | `TheFarmerWasReplacedThread()`는 탭 수 문자열을 정수로 읽음. `BongoCatServerThread()`는 장착 아이템의 버프 목록을 JSON으로 보냄 | 합성 명령·임의 메서드 실행 디스패처 없음. 파이프에 요청을 보내지 않음 |
| 명령행 | `CommandLineJoiner`가 `+connect_lobby` 처리 | 로비 입장 용도이며 합성 경로 아님 |
| 현재 채팅 앱 | `steam.py`의 Steam 로비 송신·아이템 정의 조회, `memory.py`의 조회·읽기 권한 메모리 접근 | 게임 메서드를 호출하는 연결 없음 |
| Mono embedding API | 설치된 Mono DLL에 `mono_runtime_invoke`, `mono_thread_attach`, `mono_get_root_domain` export 존재 | 같은 런타임의 객체·실행 문맥을 다루는 API. export만으로 다른 프로세스의 게임 함수를 호출할 수 없음 |
| Mono soft debugger | 디버거 에이전트와 소켓 프로토콜이 별도로 필요한 기술 | 이 게임의 사용 가능한 디버그 연결은 확보·검증하지 못함. 게임 미실행 상태이고 `boot.config`만으로 디버그 기능 부재를 단정하지 않음. 제품 경로로 채택하지 않음 |
| 기존 Auto Chest | `MainCat.Update()`에 연결된 `AutoChest.Tick()`이 게임 내부에서 실행됨. 설정은 상자 자동 열기 옵션을 처리 | 별도 패치 방식. 현재 helper에 합성 명령·범용 외부 함수 호출 기능 없음. 확장은 기존 자동화·게임 내부 코드 변경 범위 |
| Steam Inventory `ExchangeItems` 직접 호출 | 호출자가 생성 아이템과 소모할 아이템 인스턴스·수량을 지정하는 API | 원본 중복 선택 재사용과 다른 설계. 현재 앱의 실제 교환도 미검증. 사용자 합의 없이 대체하지 않음 |

Mono 공식 문서는 embedding을 호스트 애플리케이션의 런타임·주소 공간 안에서 실행하는 구성으로 설명하며 인스턴스 메서드에 객체 포인터를 요구한다. 별도 Python 프로세스에서 같은 DLL을 로드하는 것은 이미 실행 중인 게임의 인스턴스를 얻는 방법이 아니다. [Mono embedding](https://www.mono-project.com/docs/advanced/embedding/)

Soft debugger는 게임 쪽 런타임의 에이전트와 통신해야 한다. 일반 함수 export와 외부 디버그 연결은 구분한다. [Mono soft debugger](https://www.mono-project.com/docs/advanced/runtime/docs/soft-debugger/)

Steam 교환 API는 재료 인스턴스·수량을 명시적으로 받는다. 게임 UI의 즐겨찾기·이벤트 제외·종류별 1개 보존 정책을 자동으로 실행하는 API로 해석하지 않는다. [Steam Inventory ExchangeItems](https://partner.steamgames.com/doc/api/ISteamInventory#ExchangeItems)

## 범위 변경을 승인할 경우의 연결 설계안

다음은 검토용 설계안이며 구현·설치 승인이나 검증 완료를 뜻하지 않는다.

```text
채팅 앱의 합성 패널 → 합성 전용 로컬 요청 → 게임 내부 연결 모듈
  → Unity 메인 스레드의 원본 중복 선택·합성 함수 → 해당 요청의 결과 회신
```

1. 앱에서 **캐릭터·모자·봉고 / 이모티콘·UI 테마** 그룹을 선택한다. 게임 탭을 사용자가 직접 열어 두는 흐름에 의존하지 않는다.
2. 연결 모듈은 그룹·설정·가능 횟수·상태 조회와 명시적 시작·중지만 제공한다. 임의 타입명·메서드명 또는 코드 실행 요청은 받지 않는다. 로컬 연결 접근 제어·대상 프로세스·계정 확인도 설계한다.
3. 중복 선택은 원본 함수를 호출한다. 가능 횟수 조회에 슬롯을 바꾸는 `SlotDuplicates()`를 사용하는 것은 읽기 전용 조회가 아니므로 별도 검토한다. 그룹·보호 정책의 같은 시점 관측이 필요하다.
4. 기존 수동 선택·진행 중 교환·설정·그룹을 확인한다. 원본 선택 후 실제 배치 횟수가 남은 사용자 상한을 넘지 않는지 검사한다. `_possibleExchanges`를 전체 인벤토리의 최대 횟수로 사용하지 않는다.
5. 결과는 해당 교환의 콜백으로 확인한다. 미확인 요청을 재전송하거나 빈 슬롯을 성공으로 간주하지 않는다. 중지는 새 요청을 막으며 이미 접수된 교환의 취소를 약속하지 않는다.
6. 게임 업데이트 호환성, Auto Chest와의 실행 충돌, 메뉴 닫힘·포커스 변경·최소화, 재시작, 실제 보존·소비·보상을 인수 항목으로 둔다. 내부 모듈 변경에는 설치·복구 절차도 필요하다.

## 현재 결과와 검증 수준

실제 호출 경로는 추가하지 않았다. UI·세션 제어 초안은 `UnavailableGameUI`로 차단된 상태를 유지한다. 화면 클릭 어댑터를 다음 구현 과제로 이어 가지 않는다. 현재 미완료 사유는 화면 협조 부족이 아니라 **원본 함수 호출을 전달할 연결 방식과 제품 범위가 결정되지 않은 것**이다.

확인한 것은 정적 호출 구조·IPC 처리 범위·로컬 원본 백업 대비 메서드 본문 차이·씬의 초기 오브젝트 구성이다. 실제 함수 호출, 비표시 실행, 실제 합성 횟수·아이템 보존·보상 수령은 미검증이다. 이번에는 정적 조사와 문서 변경만 했으며 제품 구현 테스트를 새로 실행하지 않았다.

## 후속: 실행 중인 게임의 읽기 전용 확인

같은 날 사용자가 이 PC에서 게임을 실행한 뒤 직접 확인을 요청했다. ‘한 번에 2개 이상 테스트하지 말 것’은 **각 요청당 합성 1회**, 이번 확인 전체에서 최대 2회로 적용한다. 이는 실제 소비 시험의 제한이며 제품의 사용자 설정 상한을 1로 바꾸는 요구는 아니다. 결과가 미확인인 요청도 예산을 사용한 것으로 취급하고 자동 재시도하지 않는다.

현재 프로세스의 실행 파일·생성 시각을 식별하고, 지원되는 Mono 파일 해시·로드된 메타데이터 접근 코드·클래스·초기화된 vtable을 검증한 뒤 `ItemExchange.Instance`와 `CatInventory.Instance`를 찾았다. `OpenProcess`의 조회·읽기 권한과 `ReadProcessMemory`만 사용했다. 게임 코드 실행, Steam 교환 API, 프로세스 쓰기, 패치·주입은 없다. 조사 스크립트는 비공개 자료 경로의 `read_live_merge.py`이며 제품 어댑터로 연결하지 않았다.

| 실제 조회 항목 | 확인 결과 |
| --- | --- |
| 합성 화면 표시 | 닫힘 (`IsVisible=false`) |
| 합성 관리자 인스턴스 | 화면이 닫힌 상태에서도 조회됨 |
| 현재 그룹 | 탭 인덱스 0, 캐릭터·모자·봉고 그룹 |
| 즐겨찾기 포함 | 꺼짐 |
| 이벤트 아이템 제외 | 켜짐 |
| 합성 슬롯 | 총 10개 중 선택된 슬롯 0개 |
| 선택된 배치의 교환 횟수 | 0회. 전체 인벤토리의 합성 가능 횟수가 아님 |
| 합성 진행 | 없음 |
| 인벤토리 | 초기화 완료, 조회 진행 중 아님 |

실제 창을 캡처하고 메뉴를 열려고 했지만, 입력 도구는 해당 지점이 투명 게임 창 아래의 Chrome에 속한다고 판정했다. 게임 활성화와 새 화면 조회 후 1회 재시도했으나 같은 오류여서 더 입력하지 않았다. 게임 접근성 트리에는 창만 있고 메뉴 항목은 제공되지 않았다. 메뉴를 실제로 열거나 포커스 변경에 따른 닫힘을 재현했다고 기록하지 않는다. 이후 읽기 전용 표본에서도 선택된 재료·진행 중 합성이 없었다.

이 시점까지 **원본 함수 호출 0회, 합성 요청 0회, 이 시험으로 소모한 재료 0개**다. 화면을 열지 않고 상태를 읽을 수 있다는 점은 실제로 확인했으나, 숨긴 상태에서 원본 함수를 실행할 수 있다는 검증은 아니다. 실제 소비 시험 요청과 기존 게임 내부 모듈 추가 제외 범위를 구분해 연결 모듈 개발·설치 허용 여부를 사용자에게 확인했다. 답변 전에 해당 변경을 진행하지 않는다.
