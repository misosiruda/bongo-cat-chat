# 게임 업데이트 대응

## 이용자에게 일어나는 일

Bongo Cat Chat은 게임을 패치하지 않는다. Auto Chest Opener도 필수 조건이 아니다. 게임 업데이트 때 사용자가 게임 DLL을 재패치할 필요가 없다. 실행 중인 게임 프로세스가 바뀌면 연결을 다시 만들고 주소를 새로 찾는다.

`0.1.0.dev6`부터 게임 관리 DLL의 전체 해시 대신 기능 계약을 확인한다. `Assembly-CSharp.dll`·`Heathen.Steamworks.dll`에서 앱이 사용하는 채팅·숨김·로비·프로필 구조와 관련 처리 코드가 같으면, 알려지지 않은 빌드 번호나 달라진 DLL 파일도 연결한다. 코드와 무관한 메타데이터 토큰·RVA·MVID·파일 배치 변경은 비교하지 않는다.

관련 계약이 달라지거나 검사에 실패하면 상대 대화 표시·신규 저장과 송신을 보류하고 앱의 GitHub Release 확인을 요청한다. 같은 결과로 재시도할 때마다 요청을 반복하지 않고 기존 6시간 주기의 확인을 따른다. 빌드 번호는 안내용이며 지원을 허용하는 근거가 아니다. 실행 중 게임 파일이 바뀌어도 다음 상태 조회와 송신 직전에 감지하여 다시 검사한다.

대응 앱이 정식 Release로 게시되면 서명·해시를 검증해 자동 다운로드하고 다음 앱 실행에 적용한다. 사용 중인 앱·게임을 강제로 종료하지 않는다. 아직 대응 Release가 없거나 네트워크·서명 검증이 실패하면 연결 차단을 유지한다. 자동 업데이트가 없는 이전 dev1은 새 설치판으로 한 번 전환해야 한다. 자세한 동작은 [자동 업데이트](automatic-updates.md)를 따른다.

관련 구현 자체가 달라지면 개발자가 구조를 확인하고 대응 앱을 배포해야 한다. 사용자는 앱의 자동 업데이트 경로로 받는다. 임의의 새 코드를 의미적으로 동등하다고 추측하거나, 읽기 실패를 숨긴 사람 없음으로 처리하지 않는다. GitHub에 코드를 push한 것만으로 이용자의 설치본이 갱신되지는 않는다.

## 기능 검사와 남은 범위

[기능 계약](../src/bongo_chat/feature-contract.json)은 네 영역의 필드 형식·속성, 선택한 메서드와 참조하는 두 게임 어셈블리 안의 메서드·필드를 정규화해 비교한다. 로비 값에 쓰는 경로도 포함한다. `OnLobbyChatMsg`는 채널 선택 전 처리와 채널 3으로 도달하는 분기만 비교하므로 다른 상자·이모트 채널의 코드 변경만으로 차단하지 않는다. 해석할 수 없는 새 분기 구조는 보류한다.

Mono 런타임과 Steam 네이티브 DLL은 현재 확인된 파일로 제한한다. 특히 읽기 전용 Mono 조회는 런타임 내부 구조에 의존하므로 관리 DLL의 기능 검사만으로 미확인 런타임을 허용하지 않는다. 따라서 **모든 종류의 DLL 업데이트를 자동 호환한다고 보장하는 구현은 아니다.** 게임 기능과 무관한 관리 DLL 변경에 대해 매번 지원 목록을 수정하던 문제를 해결한 범위다.

검사에는 [Mono.Cecil](https://github.com/jbevain/cecil)의 정적 메타데이터 읽기를 사용한다. 게임 어셈블리를 실행용으로 로드하거나 메서드를 호출하지 않는다. 빌드 시 [고정 패키지](https://www.nuget.org/packages/Mono.Cecil/0.11.6)의 SHA-256을 확인하고 Windows .NET Framework 검사기와 라이브러리·MIT 고지를 앱에 포함한다. 사용자는 컴파일러·개발 도구를 설치하지 않는다. 개발 실행 전에는 `powershell -NoProfile -ExecutionPolicy Bypass -File tools/prepare-compatibility.ps1`을 한 번 실행한다. 검사 프로세스는 창 없이 실행하고 20초 제한·종료 요청·결과 크기를 확인한다.

## 2026-10-14에 확인한 오류와 수정

기존 지원 기준은 빌드 `25723683`의 네 파일 SHA-256 조합 한 개였다. 사용자의 설치는 빌드 `25902419`였고 `Assembly-CSharp.dll`·`Heathen.Steamworks.dll`이 변경됐다. Steam 네이티브 DLL과 Mono 런타임의 해시는 같았다. 사용자는 게임 업데이트 후 Auto Chest Opener를 다시 적용했다고 확인했다. **순정 환경 검증이 아니다.**

읽기 전용 정적 분석에서 다음을 확인했다.

- `PlayerDataCache`, 중첩 `PlayerData`, 로비 사용자의 숨김·표시와 이름 관련 타입은 이전 보관 IL과 일치했다.
- `LobbyData.Current`·`_id`와 사용자 이름의 친구 별명 우선 규칙, 일반 채팅의 `Channel=3`, `Message`, UTF-8 JSON 송수신 경로를 확인했다.
- 외형에는 `bongos` 장식 항목이 추가됐다. 앱의 스킨·모자 정지 프로필 범위는 유지한다. 새 장식·동작을 렌더링했다고 주장하지 않는다.

초기 실제 읽기 검사에서 후보 주소 79개를 검색하는 단계가 120초 제한에 걸렸다. 정렬된 8바이트 포인터를 한 번 순회해 찾도록 수정했다. 이름 문자열 검색, 4 GiB 읽기 예산, 단계별 120초 제한, 중복 후보·구조·프로세스 수명 검사와 실패 시 차단은 유지한다. 이전에 저장한 프로세스 주소는 사용하지 않았다.

수정 후 별도 외부 프로세스에서 주소 탐색 **42.6초**, 이후 **30초** 동안 `ready` 상태를 관찰했다. 프로필 **21개**, 상대 숨김 캐시 항목 **20개**를 읽었다. 이 구간에 해석한 채팅 콜백은 **0건**이었다. 송신·로비 변경·메모리 쓰기·대화 원문 저장은 모두 **0**이며, 검사 종료 후 게임 프로세스는 유지됐다. 이것은 연결·조회 증거이며 새 빌드의 실제 메시지 송수신 증거가 아니다.

`0.1.0.dev5`의 PyInstaller 실행 파일에서도 실제 게임에 읽기 전용으로 연결했다. Qt 화면과 작업자가 `ready`를 확인했고 프로필·스킨/모자 정지 렌더링 **22개**, 콘솔 오류 **0**, 저장 메시지 **0**, 송신 비활성 상태를 확인했다. 별도 진단 데이터 폴더와 오프스크린 Qt를 사용했다. 사람 눈으로 게임 화면과 고양이 외형을 대조한 결과는 아니다. 전체 소스 검사 **135개 통과**와 [식별정보 없는 근거](evidence/2026-10-14-game-build-compatibility.json)를 함께 보관한다.

dev5의 두 검증 환경은 [이전 파일 목록](evidence/2026-10-14-dev5-file-catalog.json)에 보존했다. dev6은 이 목록을 런타임 승인에 사용하지 않는다. 기능 계약의 빈 목록·누락된 항목·읽기 실패도 지원으로 처리하지 않는다.

## 2026-10-14 기능 계약으로 전환한 후의 검사

- 독립적으로 생성한 합성 .NET DLL로 재빌드·메타데이터 순서·무관한 상자 코드·다른 채널 변경이 허용되는 것을 확인했다. 실제 게임 DLL이나 그 복사본을 패치해 시험하지 않았다.
- 숨김 의미를 바꾸는 하위 함수, 숨김 필드 형식, 송신 채널, 채팅 수신 분기·배선, 패킷 필드 변경은 해당 기능 지문이 달라졌다. 누락·잘못된 DLL은 검사 실패다.
- 최종 계약에는 두 어셈블리 안에서 숨김 필드에 직접 쓰는 경로와 게임의 숨김 적용 메서드도 포함했다. 파일 상태의 한 번 읽기·네이티브 초기화 전·송신 직전 재확인과 회귀 검사를 추가한 최종 소스에서 **전체 154개가 78.27초에 통과**했다.
- 숨김 쓰기 경로를 추가하기 전의 소스 검사에서는 현재 게임의 주소를 새로 찾는 데 51.69초, 이후 15초 `ready` 유지, 프로필 25개·숨김 캐시 28개를 확인했다. 해석한 채팅 콜백·송신·로비 변경·메모리 쓰기·대화 원문 저장은 0이다. 검사 종료 후 게임 프로세스가 유지됐다. 확장한 최종 계약은 아래 별도 실행 파일 검사에서 확인했다. 실제 상대 화면과 순정 설치 검증은 아니다.
- 최종 설치본의 별도 실행 파일에서도 오프라인 화면과 실제 게임의 읽기 전용 연결이 종료 코드 0으로 통과했다. 프로필 24개·렌더링 23개·JS 콘솔 오류 0·저장 메시지 0·송신 비활성이다. 설치본에 포함된 검사기를 사용했으며 개발 도구를 PATH에서 제외했다.
- 전체 UI 검사와 동시에 실행한 중간 시험 한 번은 GPU context 오류와 `0x80000003` 종료로 연결 보고서를 만들지 못했다. 같은 최종 파일을 단독 실행한 재검사는 통과했지만 GPU 진단 메시지는 남아 있어 원인을 확정하거나 그래픽 안정성 문제가 해결됐다고 표현하지 않는다. 실패한 시험의 남은 작업자만 정리했다. 게임·Steam은 종료하지 않았다.
- 기존 사용자 설치에 dev6을 적용하고 설치된 실행기로 오프라인 화면을 확인했다. 이전 dev5와 실제 대화 파일 해시를 보존했다. [식별정보 없는 근거](evidence/2026-10-14-feature-compatibility.json)와 [설치 기록](installer-validation.md)을 함께 본다. GitHub 릴리스 게시는 이 작업에서 하지 않았다.

## 검증 경계

새 빌드의 실제 숨김·해제 조작, 상대 게임 화면의 송신 확인, 로비 이동·재연결·장시간 실행, 순정 설치와 다른 PC는 별도 인수가 필요하다. 사용자에게 게임 재시작이나 로비 이동을 시키지 않았다. 이전 빌드의 사용자 송신 확인을 새 빌드 검증으로 옮겨 적지 않는다.

원본 IL과 진단은 Git 제외 경로 `research/private/2026-10-14-compatibility/`에 보관한다. 공개 근거에는 클래스·검사 결과·수치만 남기며 식별정보·게임 바이너리·원문 대화를 포함하지 않는다.
